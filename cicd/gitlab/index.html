基于 Gitlab 的研发自动化体系

个人项目和没有运维需求的小团队，本书优先推荐 GitHub + Actions；公司已有 GitLab，就把它的 MR、Runner 和发布链路用好。 不要为了几个前端仓库先给自己增加一台必须持续升级和备份的服务器。

这是按维护成本给出的个人建议。有内网、数据管理或统一身份需求的团队，自托管 GitLab 可能很合适。

这篇的目标是跑通一条链路：提交分支 → MR 自动验证 → 合并默认分支 → 发布已验证的产物。先把这条链路做实，再谈更多平台集成。

GitLab 的核心功能

Section titled “GitLab 的核心功能”

前端团队先使用四项就够：仓库、Merge Request、流水线和产物。Issue 管需求，MR 看差异，CI 验证，部署任务发布。把发布结果和提交关联起来，出错知道回退哪一版。

安装 GitLab

Section titled “安装 GitLab”

只想试 CI，不必安装 GitLab 服务端。 使用团队已有实例或 GitLab.com 项目即可。确实需要自托管，再准备受支持系统、域名、HTTPS、备份存储与升级窗口。

EE 安装包可在没有付费许可证时使用 Free 层功能，别把安装包名称和订阅混为一谈。首次管理员登录、证书与系统支持按官方安装指南完成；示例中的域名不能直接当作自己的生产地址。

推荐的服务器配置

Section titled “推荐的服务器配置”

先按官方资源要求预算：当前单节点基准是 8 vCPU、16GB 内存，不再推荐把「随便一台 4GB 小机器」当公司正式代码平台。磁盘单独给 Git 历史、镜像、产物、日志与备份留空间。

GitLab 主服务和 CI Runner 分开。 构建突然吃满 CPU、内存或磁盘时，不应顺手把全公司的代码平台一起拖慢。上线前至少做一次备份恢复演练，确认代码与配置能恢复，不能只确认「备份命令成功」。

如何使用 GitLab 搭建代码托管系统

Section titled “如何使用 GitLab 搭建代码托管系统”

创建项目

Section titled “创建项目”

按团队建立 Group，再建 Private 项目，把 README、锁文件和 Node 版本文件提交进去。开发者先从分支提 MR，不直接向默认分支推送。

代码管理与权限配置

Section titled “代码管理与权限配置”

默认分支设置保护，限制直接推送；MR 配置必要评审和流水线通过条件。Runner、发布变量和生产环境的访问范围也要对应项目，别把所有成员都设成 Maintainer 来解决权限报错。

注意事项

Section titled “注意事项”

提交配置前用 CI Lint验证；任务 pending 时先看 Runner、标签和保护状态，任务已启动再看脚本日志。不要把两种问题混在一起，反复改 YAML 碰运气。

使用第三方平台部署全栈应用

Section titled “使用第三方平台部署全栈应用”

先按部署建议选托管服务。需要发容器时，把构建镜像和部署分开：先推带提交 SHA 的镜像，部署任务再让目标环境运行它；步骤见 Docker 指南。

Kubernetes 只在团队已经有集群和维护能力时使用，GitLab 集成选择 GitLab Agent。不要为了上线一个普通前端站点，先搭 GitLab、容器仓库和 K8s 三套平台。

发布 NPM 包

Section titled “发布 NPM 包”

GitLab.com 支持的受信流水线优先采用 npm trusted publishing，在 npm 中配置仓库与 CI 文件身份，通过 OIDC 发布。GitLab 的 ID token audience 需按文档设为 npm:registry.npmjs.org；自托管 GitLab / Runner 不要假定自动具备相同支持。

必须使用 Token 的环境，把它设成范围受限、Masked、Protected 的 CI/CD 变量，只给受保护发布任务使用。发布前执行 npm pack --dry-run 看清实际包内容，再运行测试、构建和 npm publish；不要把源码里的本地配置一起发布。

发布客户端应用

Section titled “发布客户端应用”

构建完成后上传安装包到受控存储，再在 GitLab Release 关联版本、变更说明与附件。Windows/macOS 的签名凭据只交给对应的发布任务，别让普通 MR 构建拿到它们。

注意事项与常见问题

Section titled “注意事项与常见问题”
现象优先排查
job 一直 pendingRunner 是否在线、标签是否匹配、是否限制保护分支
npm ci 报错锁文件是否同步，Node/npm 版本、私有 registry 认证是否正确
image 写了却没有效果Runner 是否使用 Shell executor
本地成功、CI 找不到文件大小写、漏提交文件、工作目录与实际产物目录
PR 可以构建，标签发布读不到变量变量和标签的 Protected / Environment scope 是否对应
部署 job 没拿到 dist/artifacts、needs / 下载配置和产物保留期
服务一跑构建就变慢Runner 是否与 GitLab 共用资源，是否并发过高或磁盘已满

平台集成只增加当前确实需要的通知。先让失败的构建能被负责人看见，不必把每个仓库事件推到所有聊天群。
